# Chat fixtures: provenance

Date of capture: 2026-10-23 (CDT). Claude Code 2.1.309 (`claude_code_version` in every init line). Binary: the real `~/.local/bin/claude`, run in a fresh `mktemp -d /private/tmp/clawd-p1.XXXXXX` folder, never in the repo. The run executed the user's own SessionStart hooks (four hook_started / hook_response pairs per session).

Raw captures are not committed (they hold the user's name and paths). They stay in the session scratchpad; each fixture below is the sanitizer's output on one raw file. `scripts/check-chat-fixtures.py` refuses a fixture in this folder that still holds a home path, a user name, an email or a long token-like run.

Command (all three P-1 runs, flags differ only in the permission part): `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --session-id <uuid> <permission flags>`, user lines `{"type":"user","message":{"role":"user","content":"<text>"}}`. Sanitizing: `/Users/<name>` becomes `/Users/example`, any `<name>` (case-insensitive) becomes `example`, email addresses become `user@example.invalid`; in the init line `tools`, `mcp_servers`, `slash_commands`, `skills`, `agents`, `plugins` are cut to at most 3 generic entries and `memory_paths` and `messaging_socket_path` are replaced; `commands_changed` commands are cut to two; hook output text other than the empty object is replaced; thinking `signature` strings are replaced by `SIG`. Round 2 added: every UUID (session ids, hook ids, message uuids) becomes `00000000-0000-4000-8000-<12 digits>`, numbered in order of first appearance with each file's session id first and the same placeholder wherever it repeats in that file (so "the same session id across turns" still holds); the random `/private/tmp/clawd-p1.<6 chars>` folder becomes `/private/tmp/clawd-p1.example` and the scratchpad path `/private/tmp/claude-501/-Users-<name>/<uuid>/scratchpad` becomes `/private/tmp/example-scratchpad`. The sanitizer is a short Python script kept with the raw captures in the session scratchpad (not committed: it names the owner); its round-2 output on the raw files is what is committed here.
Round 3 (2026-10-27, before sharing the repository): the 7 real API message ids (`msg_011C…`, in `api_message_id` and `message.id`)
became `msg_000000000000000000000001` … `…07`, numbered in order of first appearance across the four files, the same placeholder

## P-1 findings

Init `permissionMode` per bypass form (this is what decides the contract):
- `--permission-mode bypassPermissions` alone: `bypassPermissions`. This is the F2.1 form and it stands; `--allow-dangerously-skip-permissions` is not needed.
- `--permission-mode bypassPermissions --allow-dangerously-skip-permissions`: `bypassPermissions`.
- `--dangerously-skip-permissions`: `bypassPermissions`.
- `probe.jsonl` (no permission flag): `default`.

Block order (measured in all three P-1 files, round 4): per content block the lines come as content_block_start, content_block_delta (any number), the block's final `assistant` line, content_block_stop. A final `assistant` line therefore sits after its block's last delta and before that block's stop; thinking and tool_use blocks have the same shape. Each API message has its own `api_message_id` (four in the two-turn run). The transcript pairs a final text with the text block that is open (started or streamed, not stopped) in its message.

Stream (two-turn run):
- Line kinds in order per session: 4x `system/hook_started`, 4x `system/hook_response`, `system/init`, `system/commands_changed`, then per API request `system/status` (`requesting`), `stream_event`s, `assistant`, `rate_limit_event`, `user` (tool_result), and one `result` per turn.
- stream_event kinds: message_start, content_block_start (thinking, text, tool_use with id and name and empty input), content_block_delta (thinking_delta, signature_delta, text_delta, input_json_delta), content_block_stop, message_delta, message_stop. Every stream_event carries `parent_tool_use_id` (null here), `session_id`, `uuid` and `api_message_id`.
- `assistant` lines come once per completed content block, not once per message: the same `message.id` repeats, each line holding exactly ONE block (a thinking block, a text block, or a tool_use with its full `input`), so the k-th text block of a message is the k-th `assistant` line of that id that carries text. The final text of a message is in its `text` block; text_delta pieces concatenate to it.
- `user` lines carry `tool_result` {tool_use_id, content, is_error}; `is_error` is absent on a successful Write and `false` on a successful Bash.
- Two turns: two `result` lines, both `subtype=success`, `is_error=false`, `session_id` equal to the given id; `num_turns` 1 then 3 (cumulative per result, not reset); `total_cost_usd` is cumulative across turns (0.480 then 0.576), so a turn's cost is the difference, as F3 says.
- `system/init` appears once per turn (two in the two-turn run), not once per process; same `session_id` both times. The init `session_id` equals every result `session_id` in each P-1 run. The id the driver passed was not preserved; the session file Claude Code wrote under `~/.claude/projects/` is named with the init id, which is consistent with init == requested but is not a direct comparison (open item with the exit status).
- `rate_limit_event` (status `allowed`, `rateLimitType`, `resetsAt`, `utilization` under `unifiedWindows`) appears after each API request.
- The file hello.txt was created in the temp folder with content `hi` (Write tool, then Bash `cat`).
- Exit status at stdin EOF: NOT RECORDED. The driver printed it to a terminal that was lost; P-1 was not re-run on resume. Open decision for the main session (one cheap re-run of the allow form would settle it).

Two measured facts of these captures differ from the spec's text, and Clawd handles them as Orca does (Sprint 4):
- The CLI emits `idle` before a missed steer's own turn (d-steer-miss: the first result, `completed`, `idle`, then `running`, `queued`, `started` and the replay of the steer). Orca's rule is the same: only `idle` ends a turn (MC/claude-session-state-turn-over.ts:1-23), and a replay, `started` or `running` for a send Clawd wrote while no turn runs starts a turn Clawd did not start (the Stop control shows and the queue holds). The test plays the lines as captured; it moves the steer's `queued` frame ahead of the first turn's `idle` only to cover Orca's other miss shape (MC/claude-captured-fold-steer-frames, test-fixture file, lines 113-149).
- An interrupt cancels the running command but not a queued steer: the control_response lists it in `still_queued` and it then runs as its own turn (d-steer-cancel, lines 85 and 89 to 127). Orca does not leave it there. A CLI that advertises `interrupt_cancel_queued_v1` in its init (every init of these captures does) gets `cancel_queued: true` in the interrupt itself and the receipt's `cancelled` list settles those sends as cancelled; any other CLI gets one `cancel_async_message` per `still_queued` uuid and each answer `cancelled: true` settles that send (MC/claude-structured-control-actions.ts lines 36-52, claude-agent-sdk-control-requests.ts lines 90-140; wire form in Orca's lifecycle captures, cancel-async and interrupt-lost, under MC/__fixtures__). Clawd does the same. The captures themselves were taken before that handling, with the plain interrupt, so d-steer-cancel and d-steer-fold-then-interrupt still show the CLI's own behaviour (the receipt's request id is the driver's, which Clawd's request id does not match, so Clawd writes nothing for it). The two new tests write the init, the receipts and the answers out whole (the two interrupt tests in ChatOrcaParityDSteerTests); no capture of a withdrawn steer was taken, so those two frame shapes are Orca's, not measured on 2.1.312.
